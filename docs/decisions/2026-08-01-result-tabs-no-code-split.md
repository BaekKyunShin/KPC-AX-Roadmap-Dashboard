# 결과 화면 탭은 코드 분할하지 않는다

**Date:** 2026-08-01
**Status:** Accepted

## Context

서울 리전 이전(#159·#160)으로 네트워크 지연이 사라지자, 남은 체감 시간에서 브라우저의 JS 다운로드·파싱·하이드레이션 비중이 상대적으로 커졌다. 성능 감사는 결과 화면 3종을 후보로 지목했다 — 한 번에 탭 하나만 보이는데 전 탭 코드가 초기 청크에 들어 있었다.

| 화면                                        | 탭  | 탭 본문 합계 |
| ------------------------------------------- | --- | ------------ |
| 로드맵 결과 (`RoadmapResultClient`)         | 3   | 676줄        |
| PBL 결과 (`PBLResultClient`)                | 4   | 1,987줄      |
| 갤러리 PBL 상세 (`GalleryPBLDetailContent`) | 5   | 1,816줄      |

`next/dynamic` 으로 분리하되, **탭 전환이 종전처럼 즉시 이뤄지도록** 마운트 직후 `requestIdleCallback` 에서 나머지 탭을 프리페치하는 설계로 #164 를 머지했다. "기능·UI·UX 불변, 속도만 개선"이 전제였다.

## Decision

**결과 화면 탭 본문은 `next/dynamic` 으로 코드 분할하지 않는다.** #164 를 #167 로 원복한다.

실측 결과 이 분할은 **순손실**이다 — 초기 진입에서 16ms 를 얻고 탭 전환에서 342ms 를 잃는다. 그것도 사용자가 직접 체감하는 클릭 반응에서.

## Alternatives

- **분할 + 유휴 시점 프리페치 (= #164 가 한 것):** 채택했다가 원복. **프리페치가 동작하지 않는다** — 아래 Verification 참조.
- **분할만 하고 프리페치 없음:** 더 나쁘다. 탭 전환 지연에 더해 로딩 스켈레톤이 매번 눈에 보인다.
- **프리페치 실패 원인을 규명해 살리기:** 성공해도 상한이 **초기 진입 16ms** 다. Next.js 내부 청크 그룹 동작을 파고들 만한 가치가 없다고 판단했다.
- **`ResultTabs` 에 `forceMount` 를 붙여 전 탭 선렌더:** 분할과 무관하게 초기 렌더 비용만 늘린다. 검토 후 기각.

## Consequences

- **Pros**
  - 탭 전환이 59ms 로 유지된다(분할 시 401ms)
  - 로딩 스켈레톤이라는 신규 UI 요소가 사라져 "UI 불변" 전제가 지켜진다
  - 결과 화면 관련 코드가 단순해진다(dynamic 래핑·프리페치 effect 제거)
- **Cons**
  - 초기 진입이 16ms 느리다 (498ms → 514ms, 로컬 실측)
  - 결과 화면의 임계 경로 JS 가 약 55KB 크다
  - 향후 탭 본문이 크게 불어나면 재검토가 필요하다 — 그때는 **분할이 아니라 탭 본문 자체를 줄이는 쪽**을 먼저 보라

## Verification

로컬(`next start` 프로덕션 빌드 + 로컬 Supabase)에서 같은 화면을 대상으로 분할만 켜고 끄며 3~5회 반복 측정했다. 대상은 시드기업D 의 로드맵 결과 화면.

| 지표                            | 분할 적용 | 분할 없음 | 차이                  |
| ------------------------------- | --------- | --------- | --------------------- |
| 초기 진입 (첫 탭 내용 표시까지) | 498ms     | 514ms     | 분할이 16ms 유리      |
| **탭 전환 (Ⅲ. 훈련체계)**       | **401ms** | **59ms**  | **분할이 342ms 불리** |
| 탭 전환 (진입 직후 즉시)        | 135ms     | 32ms      | 분할이 103ms 불리     |
| 임계 경로 JS                    | 1,382.7KB | 1,437.6KB | 분할이 54.9KB 유리    |

**프리페치가 동작하지 않는 것을 직접 확인했다.** 페이지 진입 후 3초를 기다린 뒤 탭을 눌러도 그 시점에 청크를 새로 받는다:

```
클릭 전 JS 46개/1492KB → 클릭 후 48개/1514KB  (클릭으로 새로 받은 파일 2개)
```

`useEffect` 안의 `void import('./TabTraining')` 와 `dynamic(() => import('./TabTraining'))` 가 같은 모듈 지정자인데도 재활용되지 않는다 — Next.js 가 둘을 별개 청크 그룹으로 취급하는 것으로 보인다(원인은 끝까지 규명하지 않음).

분할이 실제로 청크를 가르는 것 자체는 확인됐다. 정적 import 로 되돌리면 탭 코드가 클라이언트 본체 청크와 합쳐진다(교집합 3/3, 본체 108.4KB → 172.6KB). 즉 **분할은 의도대로 동작했고, 그 결과가 나빴다.**

## Follow-ups

- 세 클라이언트 파일 상단에 "코드 분할하지 말 것 + 근거" 주석을 남겼다. 이 문서를 가리킨다
- `docs/PERFORMANCE_BUDGET.md` 의 「로드맵 결과 화면 임계 경로 JS」 예산은 **분할 없는 상태 기준**으로 다시 잡는다(#165)
- 재검토 조건: Next.js 가 `next/dynamic` 프리페치를 공식 지원하게 되거나, 탭 본문이 현재의 몇 배로 불어나 초기 진입이 실제로 문제가 될 때
- 일반화된 교훈: **"이렇게 하면 빨라질 것"은 가설이다.** 최적화는 전후를 같은 조건에서 재고 나서야 최적화다. #164 는 재보지 않고 머지했다가 되돌렸다
