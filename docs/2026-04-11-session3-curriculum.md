# 1. 메타 프롬프트 + Plan 모드 시연

**이걸 왜 알아야 하나**: 기획서를 붙여넣고 "이대로 만들어줘"는 바이브코딩의 가장 흔한 실수다. 결과는 십중팔구 엉망이다. **메타 프롬프트**는 이 문제를 근본적으로 해결하는 핵심 기술이다.

**핵심 원리**

LLM은 "사람의 애매한 의도를 해석하는 것"보다 **"LLM이 이해하기 좋은 프롬프트를 만드는 것"**에 훨씬 더 강하다. 그래서 사람이 직접 프롬프트를 쓰는 대신, **Claude에게 "이 프로젝트를 위한 최적 프롬프트를 만들어줘"라고 시키는 것**이 더 효과적이다. 이걸 **메타 프롬프트** — 프롬프트를 만드는 프롬프트 — 라고 부른다.

> **비유**: 디자이너에게 "멋진 대시보드 만들어주세요"라고 하면 디자이너 취향대로 나온다. 반면 "어떤 정보가 필요한지 먼저 물어봐주세요. 그다음 와이어프레임을 보여주세요"라고 하면 결과가 **훨씬** 달라진다. 메타 프롬프트는 이 "먼저 물어봐주세요 → 그다음 계획 보여주세요"를 **자동화**한 것이다.

**실제 워크플로우 (3단계)**

1. 기획서를 Claude에 첨부하고 "이 기획서를 기반으로 만들 건데, **최적 프롬프트를 설계**해서 파일로 저장해줘"
2. Claude가 애매한 점을 질문 → 답변 → 최적 프롬프트를 `docs/prompts/` 폴더에 파일로 생성
3. **새 세션**에서 그 파일을 **Plan 모드**로 실행 → 훨씬 정확한 계획

왜 "새 세션"인가? 첫 세션은 "프롬프트 설계"라는 질문·답변 대화가 쌓여있다. 새 세션에서 **깨끗한 상태로 최적 프롬프트만 넣으면** 결과가 더 정확하다.

> **★ 핵심 하이라이트** — 전체 커리큘럼에서 가장 중요한 장면. Claude가 직접 설계한 최적 프롬프트를 `docs/prompts/`에 저장하고, 그걸 새 세션의 Plan 모드에 넣었을 때 계획 품질이 드라마틱하게 달라지는 순간.

---

### 단계 1 · 1차: 기획서 바로 붙여넣기

```
이 기획서대로 만들어줘. @docs/PROJECT_OUTLINE.md
```

→ Claude가 자기 마음대로 스택·구조·컴포넌트를 결정한 **엉성한 계획**이 나온다. 기획서에 적지 않은 세부사항은 전부 Claude가 *추측*해서 채운 결과.

### 단계 2 · 메타 프롬프트로 최적 프롬프트 설계

```
@docs/PROJECT_OUTLINE.md를 기반으로 경영진 대시보드를 만들 것이다.
Claude Code에 입력할 최적 프롬프트를 설계해서
docs/prompts/01-bootstrap.md 파일로 저장해줘.

애매한 부분은 먼저 질문하고, 기술 스택·데이터 모델·화면 구조·개발 순서까지
포함해서 한 덩어리 프롬프트로 완성해줘.
```

→ Claude가 **먼저 질문**한다 ("차트 라이브러리는 뭘 쓸 건가요?", "인증은 필요한가요?" 등). 답변을 받은 뒤 **구조화된 최적 프롬프트**를 `docs/prompts/01-bootstrap.md` 파일로 생성.

> **왜 파일로 저장하는가** — 파일로 저장하면 `@파일참조`로 한 번에 전달할 수 있고, 팀원 전체가 공유할 수 있으며, git 커밋으로 프롬프트 개선 히스토리도 추적 가능.

### 단계 3 · 새 세션 → Plan 모드 → 최적 프롬프트 실행

1. 새 터미널 탭 열기 (또는 `/clear`로 세션 리셋)
2. `Shift+Tab` **두 번** 눌러 **Plan 모드**로 전환
3. 입력: `@docs/prompts/01-bootstrap.md`
4. Claude가 Plan 모드에서 **구조화된 단계별 계획**을 출력
5. 1차(바로 붙여넣기)의 결과와 비교 → 드라마틱한 품질 차이를 확인

> **30초 개념 설명 — Plan 모드 = "먼저 생각하고 나서 실행"의 강제**
> LLM에게 "think step by step"이라고 하면 추론 정확도가 올라가는 것처럼, Plan 모드는 Claude가 **바로 코드를 쓰기 전에 계획을 먼저 펼치게** 강제하는 장치. 그 계획을 사용자가 보고 승인·수정할 수 있다.

> **짧은 시연 범위** — **Plan 모드의 계획 비교까지만**. 실제 부트스트랩·DB·UI 생성은 하지 않음.

# 2. 하네스 엔지니어링 — AI를 구조적으로 제어하는 방법

**이걸 왜 알아야 하나**: 메타 프롬프트가 "좋은 지시를 만드는 기술"이었다면, 하네스 엔지니어링은 **"AI가 그 지시를 매번 따르게 만드는 구조"**다. 이 둘이 합쳐져야 바이브코딩이 완성된다.

## 야생말과 고삐

AI는 **야생말**이다. 엄청난 능력이 있지만, 고삐 없이 타면 어디로 갈지 모른다.

- **프롬프트 엔지니어링** = 말에게 "오른쪽으로 가줘"라고 **말하는 것** (부탁). 말이 기분 좋으면 따르고, 아니면 무시한다.
- **하네스 엔지니어링** = 말에게 **고삐·안장·울타리**를 씌우는 것 (강제). 물리적으로 특정 방향으로만 갈 수 있게 제한한다.

핵심 차이: **프롬프트는 "이번 한 번" 부탁이지만, 하네스는 "매번 자동으로" 적용되는 구조적 제어**다.

Claude Code에서 쓸 수 있는 하네스는 크게 4가지다:

| 하네스 | 비유 | 강제하는 것 |
|--------|------|------------|
| `CLAUDE.md` | 신입에게 주는 온보딩 문서 | 매 요청마다 프로젝트 규칙이 자동 주입 |
| 스킬 | 업무 매뉴얼 | "설계 먼저, 코드 나중" 같은 작업 순서를 강제 |
| MCP | 스마트폰 앱 설치 | Claude가 접근할 수 있는 외부 도구를 확장 |
| 훅 | 자동 알림 시스템 | 특정 이벤트에 셸 명령이 자동 실행 |

지금부터 각 하네스를 하나씩 알아보자.

---

## `CLAUDE.md` — 가장 기본적인 하네스

**한 줄 요약**: 프로젝트 루트에 놓는 마크다운 파일. Claude Code가 **모든 요청에 자동으로** 이 파일 내용을 읽고 참조한다.

채팅에서의 "시스템 프롬프트"를 알고 있다면, `CLAUDE.md`는 **프로젝트 전용 시스템 프롬프트**라고 생각하면 정확하다. 프롬프트처럼 보이지만, **매번 자동 주입**되기 때문에 하네스다.

> **비유**: `CLAUDE.md`는 **신입 개발자에게 주는 프로젝트 온보딩 문서**다. 이걸 안 주면 매번 "이 프로젝트 스택이 뭐예요?"부터 시작해야 하고, 주면 바로 일을 할 수 있다. Claude에게도 똑같다.

**무엇을 넣는가**

- 프로젝트 한 줄 소개
- 기술 스택 (프레임워크, DB, 스타일링, 배포)
- 주요 명령어 (`npm run dev`, `npm run build` 등)
- 디렉터리 구조 간략 설명
- 코딩 컨벤션 (네이밍 규칙, 파일 배치 원칙)

**예시 — 우리 프로젝트의 `CLAUDE.md`**

```markdown
# 경영진 실적관리 대시보드

## 기술 스택
- Next.js 16 (App Router)
- Tailwind CSS + shadcn/ui
- Supabase (PostgreSQL + Auth)
- Recharts (차트)
- Vercel (배포)

## 주요 명령어
npm run dev          # 개발 서버 (localhost:3000)
npm run build        # 프로덕션 빌드

## 디렉터리 구조
src/app/             → 페이지 (App Router)
src/components/      → 재사용 컴포넌트
src/lib/             → 유틸리티, Supabase 클라이언트
docs/                → 기획서, 문서
```

**실제 사용법**

- **자동 생성**: `/init` 명령을 쓰면 Claude Code가 코드베이스를 분석해서 `CLAUDE.md`를 자동 생성
- **수동 편집**: 프로젝트 루트에 `CLAUDE.md` 파일을 직접 만들어도 됨
- **업데이트**: 프로젝트가 커지면 `/init`을 다시 실행하거나 직접 수정

> **`@파일참조` — 특정 파일을 Claude에 보여주는 법**
> `@` 뒤에 파일 경로를 입력하면 해당 파일의 내용이 Claude의 컨텍스트에 들어간다.
> - `@docs/PROJECT_OUTLINE.md` → 기획서 내용이 Claude에 전달
> - `@src/app/page.tsx` → 특정 코드 파일을 보여줌
>
> `CLAUDE.md`가 "항상 자동으로 들어가는 배경"이라면, `@파일참조`는 **"이 파일을 지금 보여줄게"** 하고 직접 지정하는 것.

## 스킬 — Claude의 "업무 매뉴얼" 하네스

**한 줄 요약**: Claude가 **어떻게 일해야 하는지**의 규칙을 정의한 마크다운 파일.

Claude는 똑똑하지만, 규칙이 없으면 자기 마음대로 한다. 바로 코드부터 짜고, 버그를 추측으로 고치고, 테스트도 안 돌려본다. 스킬은 이런 나쁜 습관을 막는다.

> **비유**: 똑똑한 신입 직원이라도 회사의 업무 매뉴얼을 안 읽으면 자기 방식대로 일한다. "우리 팀은 기능 만들기 전에 **설계 문서를 먼저 써**"라고 매뉴얼에 적어두면, 신입도 그 프로세스를 따른다. 스킬은 Claude에게 주는 **업무 매뉴얼**이다.

**스킬이 없을 때 vs 있을 때**

| 상황 | 스킬 없을 때 | 스킬 있을 때 |
|------|------------|------------|
| "새 기능 만들어줘" | Claude가 바로 코드부터 작성 | **brainstorming 스킬**: 요구사항을 먼저 탐색 |
| "이 버그 고쳐줘" | "이거 고쳐봐요 → 안 되면 저거..." 무한 추측 | **debugging 스킬**: 증거 → 가설 → 검증 순서를 강제 |
| "다 했어?" | "네, 끝났습니다" 하고 끝 | **verification 스킬**: 빌드·테스트를 실제로 돌려서 확인 |

**실제 사용법**

스킬은 `.md` 파일로 작성하고, 정해진 폴더에 넣으면 Claude가 자동으로 인식한다.

- **전역 스킬**: `~/.claude/skills/` 폴더 → 모든 프로젝트에 적용
- **프로젝트 스킬**: `.claude/skills/` 폴더 → 해당 프로젝트에만 적용
- **플러그인 스킬**: 플러그인 설치 시 자동 등록 (직접 만들 필요 없음)

Claude가 상황에 맞는 스킬을 **자동으로 선택해서 적용**한다. "brainstorming 스킬 써줘"라고 말할 수도 있고, Claude가 알아서 판단하기도 한다.

## MCP — Claude에게 "손"을 달아주는 하네스

**한 줄 요약**: Claude가 **외부 세계를 직접 만질 수 있게** 해주는 연결 장치.

Claude는 기본적으로 **텍스트를 읽고 쓰는 것**만 할 수 있다. DB에 테이블을 만들거나, 웹에서 최신 문서를 검색하려면 MCP가 필요하다.

> **비유 — 스마트폰 앱**
> 스마트폰(Claude Code)만 있으면 기본 기능은 된다. 그런데 **카카오톡 앱(MCP)을 설치해야 메시지**를 보낼 수 있고, **은행 앱(MCP)을 설치해야 송금**할 수 있다. MCP는 Claude에 **"앱을 설치"**하는 것이다.

**MCP가 없을 때 vs 있을 때**

| 상황 | MCP 없을 때 | MCP 있을 때 |
|------|-----------|-----------|
| "고객 테이블 만들어줘" | SQL 코드를 텍스트로 출력. 직접 복사해서 DB에 붙여넣어야 함 | **Supabase MCP**: 실제 DB에 바로 테이블 생성 |
| "shadcn DatePicker 사용법" | 학습 데이터 기반 답변 (API가 바뀌었을 수 있음) | **Context7 MCP**: 공식 문서를 실시간으로 가져와 최신 정보로 답변 |
| "차트 카드 컴포넌트 추가" | Claude가 코드를 추측해서 작성 | **shadcn MCP**: 레지스트리에서 최신 컴포넌트를 조회해 정확한 코드로 설치 |

**실제 사용법**

MCP 서버 등록:
```
claude mcp add <이름> -- <실행 명령>
```

예시:
```
claude mcp add context7 -- npx -y @anthropic-ai/mcp-server-context7
```

등록된 MCP 확인:
```
/mcp
```

설정 파일 위치:
- **전역** (모든 프로젝트): `~/.claude/settings.json`
- **프로젝트** (이 프로젝트만): `.claude/settings.local.json`

## 플러그인 — 하네스 묶음 패키지

스킬과 MCP를 하나하나 설치하면 번거롭다. 플러그인은 관련된 것들을 **한 번에 묶어서 설치**할 수 있게 해준다.

> **비유 — 게임의 "직업 패키지"**
> 게임에서 전사 직업을 선택하면 검술·방어·돌진 스킬이 한 번에 장착되듯, **Superpowers 플러그인**을 설치하면 brainstorming·TDD·디버깅·검증 스킬 14개가 한 번에 장착된다.

**예시**:
- **Superpowers 플러그인** 1개 설치 → 14개 스킬이 일괄 등록
- **Vercel 플러그인** 1개 설치 → Next.js·배포·AI SDK 등 38개 스킬이 일괄 등록

## 마켓플레이스 — 하네스 도구를 찾는 앱스토어

플러그인을 어디서 찾아 설치할까? **마켓플레이스**다. 앱스토어에서 앱을 검색하고 설치하듯, 마켓플레이스에서 플러그인을 찾아 설치한다.

**사용법**:
```
/plugin                              # 플러그인 관리 화면 열기
/plugin marketplace add <owner/name> # 마켓플레이스 등록
/plugin install <name>@<marketplace> # 플러그인 설치
/reload-plugins                      # 설치 후 반영 (필수!)
```
